# The fourteen incidents and their evidence

Each incident of Table 6 of the article, with the archived evidence that supports it. `archive/incidents.json` is the
machine-readable table; this file adds dates, detection, correction and the records to open.

References of the form `PROGRESS.md Lnnn` point to lines of the authors' development log, which is not part of the
package (it is a private working diary). Where an incident rests on the log alone, the article says so and the
evidence column of Table 6 is `L`; where it rests on notes alone, `N`. Paths `archive/records/...` are in this package.
File names mentioned in the evidence that are not in `archive/records/` (for example analysis scripts of the
development tree) are given for completeness; their outputs, where they matter, are reconstructed by
`archive/reconstruct/*.mjs`.

## Incident 1 (discussed in the text): host throughput drifted 32 % between batches

* layer: execution
* misleading inference: a component effect
* status: observed: the misleading conclusion was drawn
* detection: re-run of one configuration (canary)
* evidence: archived result records (archive/records/)
* safeguards: S2, S3, S4
* date: 2026-08-12 07:00Z (found and diagnosed; PROGRESS.md L2037-2038). The canary re-run row is timestamped 2026-08-12T06:52:45Z; the earlier comparison run is 2026-08-11T10:08:13Z.
* how it was detected: Canary re-run: the complete solver was re-run on the same instance and seed with identical code, and its move rate compared with the previous day's run (PROGRESS.md L1997-2003; main.tex L733-739).
* correction: Switched to move-bounded runs (--moves) as a machine-independent comparison, randomised seeded run order, and kept wall-clock runs in one uninterrupted batch. The contaminated batches were kept, not deleted (PROGRESS.md L2005-2017). This also retired the earlier '39% chain gain at n=3,200' claim (L2018-2019; README.md L155).
* affected version: v20-shipped.ts (canary rows in results.jsonl). ablation.mjs, whose default --solver is variants/v20-shipped.ts (ablation.mjs L63).
* records:
  * archive/records/results.jsonl: v20-shipped.ts, n=3200, seed 1, timeBudgetMs 30000. Row ts 2026-08-11T10:08:13Z gives iterations/solverElapsedMs = 64,375 moves/s (soft 81); row ts 2026-08-12T06:52:45Z gives 43,785 moves/s (soft 144), a 32.0% drop.
  * archive/records/ablation-contaminated.jsonl: 90 rows, the 30 s and 60 s blocked-order batches at n=3200, field movesPerSec. For config 'full' the range is 36,827-43,681 (30 s) and 36,640-43,897 (60 s); archive/reconstructed/rates.tex has the table built from them.

Note: The wrong numbers were produced and stored, and the related '39%' chain claim from the earlier study is listed as a retraction (README.md L155). The log does not say whether the 30 s/60 s tables themselves reached a draft; main.tex L729-731 says only that 'either would have been published'. The 06:52:45Z canary row has label=null and jobId=null (see incident 7).

## Incident 2 (discussed in the text): a behaviourally null configuration measured non-zero

* layer: control
* misleading inference: a 10 % ablation gain
* status: observed: the misleading conclusion was drawn
* detection: null arm; code inspection
* evidence: archived result records (archive/records/)
* safeguards: S4
* date: 2026-08-12 07:55Z (PROGRESS.md L1954, L1982-1985)
* how it was detected: Null-control cross-check. When the move-bounded batch came in, no-rcl was byte-identical to full on all five seeds. Reading the code explained it: n=3200 has 167 rooms, below the 256-room full-scan threshold, so the option never engages (PROGRESS.md L1982-1985).
* correction: No-rcl at n=3200 is treated as a deliberate null (placebo) arm. Its measured deviation is reported as that batch's null-control deviation, not as an effect. Table generated by incidents.mjs (threeviews.tex, floors.tex).
* affected version: ablation.mjs with default solver v20-shipped.ts. incidents.mjs (table).
* records:
  * archive/records/ablation-contaminated.jsonl: n=3200, timeMs 30000. Median soft is 219 for full (seeds 1-5: 144,177,275,219,224) and 197 for no-rcl (162,175,370,220,197), i.e. -10.0%. At timeMs 60000 both medians are 98 (0.0%).
  * archive/records/ablation-moves.jsonl: n=3200, budget moves 1,500,000. Configs full and no-rcl have identical per-seed soft values (107,135,207,159,155).
  * archive/reconstructed/floors.tex: \floorThirty=-10.0, \floorSixty=0.0, \floorMoves=0.0

Note: The -10% number is in the stored batch. The log does not show the inference 'RCL harmful at short budgets, neutral at long ones' being written down before 07:55Z. That inference is stated only in main.tex L773-775. main.tex says the no-op was found 'while preparing the move-bounded replacement'; the log records it when that batch's results came in.

## Incident 3: one seed per size

* layer: sampling
* misleading inference: a linear scaling law that reversed
* status: observed: the misleading conclusion was drawn
* detection: deeper sample
* evidence: archived result records (archive/records/)
* safeguards: S7
* date: Not in the development log, which starts 2026-08-12 05:05Z (L2030). It first appears there as a retraction at 2026-08-12 14:35Z (L368).
* how it was detected: Deeper sample: three or more seeds per size instead of one (README.md L156; NOTES.md L44; main.tex L839-842).
* correction: Soft cost is proportional to n^1.25, R^2=0.995 over seven sizes. scaling.mjs fits the per-size median of v20-shipped rows at the largest budget per size.
* affected version: v20-shipped.ts; scaling.mjs
* records:
  * archive/records/results.jsonl: variant v20-shipped.ts (rows used by scaling.mjs). Re-running scaling.mjs here gives soft ~ n^1.247, R^2=0.9947. Seeds per size at the budget used: 400-6400 at 120 s = seeds 1-3; 12800 at 300 s = seeds 1,1,2; 31000 at 470 s = seeds 1,2.
  * Faulty single-seed ladder: no record can be identified with certainty. results.jsonl does hold a seed-1-only v20-shipped 30 s ladder (n=400,1600,3200,6400, ts 2026-08-11T10:07-10:08Z), followed by seeds 2-5 from 10:16Z. That fits the story but is not confirmed as the ladder in question.

Note: Status rests on the retraction list (PROGRESS.md L364-370: 'a scaling law that was a single-seed artefact'; 'four of the five had been written into a draft first', without saying which four) and on README.md L156. main.tex L846-848 says the ladder 'was still being cited internally weeks later'. Literal caveat: at 12800 (300 s) only seeds 1 and 2 are used, and at 31000 only two seeds, so 'three or more seeds per size' does not hold at the two largest points of the fit.

## Incident 5 (discussed in the text): a defensive clamp silently raised requested values

* layer: configuration
* misleading inference: the parameter optimum was inside the tested range
* status: observed: the misleading conclusion was drawn
* detection: code inspection
* evidence: archived result records (archive/records/)
* safeguards: S5
* date: Discovery is recorded at 2026-08-12 07:55Z (PROGRESS.md L1978-1981). The clamp fix landed in the application repository at 2026-08-12 18:40Z (L682-690).
* how it was detected: Code inspection while preparing an ablation configuration that asked for L=1 (main.tex L886-890; NOTES.md L46). The log notes that the earlier sweeps never went below 50 because the solver silently rewrote smaller requests (L1979-1981).
* correction: Clamp relaxed from Math.max(50, L) to Math.max(1, L): timetable-ui/src/app/timetable-solver.ts:2001 and the variant copy _to_delete/variants/v20-shipped.ts:2001. Rows that had asked for L=1 but ran at L=50 were relabelled short-history (analyse.mjs L58-62). A genuine L=1 'greedy-accept' arm was re-run.
* affected version: v20-shipped.ts / timetable-solver.ts L2001 (clamp); ablation.mjs; analyse.mjs
* records:
  * archive/records/ablation-moves.jsonl: config 'short-history', keys short-history-n3200-s{1..5}-m1500000. Field note: 'L=50 - the run requested L=1 but the solver clamped the history to a floor of 50, so this row is a short history, not a greedy descent'.
  * archive/records/ablation-moves.jsonl (and later ablation-* files): config 'greedy-accept' (genuine L=1) holds the corrected rows.
  * archive/records/ablation-contaminated.jsonl: 10 'greedy-accept' rows, which incidents.mjs L66 folds into 'short-history'. That implies they too ran clamped; this is an inference from the script.
  * archive/records/results-preTravelFix.jsonl: lahcLength sweeps (labels v2-L50 ... v2-L200000) and archive/records/results.jsonl (lahcLength 50-8000). The smallest value requested in both is 50. The same file holds v1-lahc.ts jobIds cmp-L1 {lahcLength:1} and cmp-L50 {lahcLength:50} (n=100, seed 1, 2026-08-10T23:24-23:25Z), with identical hard 7 / soft 297 / objective 738710. That is consistent with the clamp but does not prove it (wall-clock runs).

Note: Clamped rows were stored under a misleading config label before the rename (analyse.mjs comment). The archived sweeps never requested below 50, so the clamp did not change their stored values; what it hid was the region below 50. The 29.1% figure (NOTES.md L205: moved from 25.9) was not re-verified here.
