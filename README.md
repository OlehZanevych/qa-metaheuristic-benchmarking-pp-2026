# qa-metaheuristic-benchmarking-pp-2026

Reproduction package for

> O. B. Zanevych, V. M. Kukharskyy. *Quality Assurance for Metaheuristic Benchmarking: Hidden
> Feasible Solutions, Independent Validation and Reproducibility Safeguards.* Problems in
> Programming (Проблеми програмування), 2026.

It contains everything needed to check the article's claims: the instance generator with its
retained feasibility witnesses, the independent validator with its micro-tests, boundary cases and
seeded faults, the timetabling solver exactly as used, the experiment designs and runner, every run
record, the analysis that turns the records into the article's tables and numbers, and the archived
historical records of the development work together with the scripts that reconstruct the
historical figures the article quotes.

The package is plain JavaScript for Node.js. It has **no dependencies**: nothing to install.

## Requirements

* Node.js **22.13 or later** (the solver is TypeScript and is loaded with Node's built-in
  `module.stripTypeScriptTypes`). Checked with Node 22.22 on Linux x86-64 and Node 22.23 on Linux arm64.
* Two CPU cores and about 2 GB of memory for the full run.

## Operations

The raw run records the article reports are `results/*.jsonl`. **No command modifies them**: a new
experiment always goes into a directory of its own. The derived files next to them (`summary.json`,
`identity.json`, `paired-observations.csv`, `tex/`) are regenerated by `./run_all.sh tables`.

| command | what it does | time |
|---|---|---|
| `npm test` | validator tests, mutation analysis, safeguard tests, quick generator self-test and identity check | seconds |
| `./run_all.sh tables` (`npm run tables`) | recomputes every number and table of the article from the supplied records in `results/` and rebuilds the historical figures from `archive/records/`; `results/tex/*.tex` come out byte-identical to the article's | seconds |
| `./run_all.sh fresh [DIR]` (`npm run fresh`) | runs the full tests, then **executes every experiment anew** into `DIR` (default `runs/fresh-<UTC time>`), then analyses `DIR` there (`DIR/summary.json`, `DIR/tex/`). Refuses a directory that already holds records | about 7 hours on two cores |
| `./run_all.sh resume DIR` | continues an interrupted fresh experiment: only the missing runs are made, and only if the records already in `DIR` were produced by the same record schema, metric version, solver/generator/validator sources and effective options (and, for wall-clock designs, the same CPU model, core count, architecture and Node version); then analyses `DIR` | the rest |
| `./run_all.sh smoke [DIR]` (`npm run smoke`) | a fresh run of the small `smoke` design (n = 400, two configurations, two replicates), checked like any other record set: new run ids and timestamps, the full counter and filter vectors, schedule hashes | seconds |

Comparing a fresh directory with `results/` shows what reproduced on your machine.

## What reproduces exactly and what does not

| result | rerun on another machine |
|---|---|
| validator tests, mutation analysis, safeguard tests, generator self-test, generator identity | identical |
| move-budget runs (designs `T3-moves`, `B-moves`, `L-sweep`; the outcomes of `drift`) | the same outcomes were observed on two processor architectures (below); elapsed times differ |
| wall-clock runs (`T3-wall30-blocked`, `T3-wall60-blocked`, `T3-wall30-shuffled`, `B-wall60`, `B-wall300`) | **different**: a wall-clock run measures the host. Expect other moves per second, other costs and possibly other signs |
| numbers and tables from the supplied records (`./run_all.sh tables`) | identical |

`results/identity.json` compares the move-budget reproduction runs (x86-64 host) with the archived
runs of the development work (arm64 host). The four archived move-budget files hold 220 rows; 175
of them have a reproduction run with the same configuration, size, seed and move budget, and all
175 agree exactly in soft cost, hard count, moves made, feasibility flag and the nine validator
counters. The other 45 rows (configurations `no-taper`, `no-hot`, `long-history`, `fixed-weight` and
`short-history` at n = 12 800) have no reproduction run and are listed in `unmatchedBy`. **Schedule
identity was not assessed**: the archived rows store no assignments, and equal summaries do not
imply equal schedules. Records written by the current runner (schema 2) carry a canonical
schedule hash (`scheduleHash`), so two fresh experiments can also be compared schedule by schedule.
All of this is an observation for the environments used, not a guarantee for all.

                                                                   -> results/generator-selftest.json
tests/generator-identity.mjs      released generator vs the generator of the historical records (tests/reference/)
                                                                   -> results/generator-identity.json

analysis/identity.mjs             reproduction runs vs archived move-budget runs -> DIR/identity.json
analysis/analyse.mjs              paired effects, 95 % intervals, interaction, L sweep, timing -> DIR/summary.json,
                                                                   DIR/paired-observations.csv

analysis/safeguards.json          the eight safeguards S1-S8 and their executable checks (Table 7)

## Run records

Each line of `<dir>/<design>.jsonl` is one run: design, configuration, requested **and effective**
solver options, instance seed, solver seed, budget type and value, moves made, elapsed time, moves
per second, whether the budget was spent, execution order and position, start time, validator
results (feasibility, hard violations, soft cost, the nine counters in `violations`), the metric
version, the SHA-256 of the solver, generator and validator sources, and the runtime environment
(Node version, CPU model, core count, memory; the host name only as a hash). Canary runs carry
`"canary": true`. Records written by the current runner (`"schema": 2`) also carry the five
legality filters (`filters`: unplaced, room, time grid, scheduling rule, duplicate), a canonical
`scheduleHash`, the `instanceHash`, a `runId` and a `batchId`. The records in `results/` were made
before these fields existed (schema 1): they hold the counters and the feasibility flag but not the
filter vector.

`<dir>/paired-observations.csv` lists every matched pair behind every effect, with its absolute
and relative difference.

## Checks before analysis

`analysis/records.mjs` accepts a set of records only when it is exactly the design's plan: every
planned run and canary present once and nothing else (a duplicate that replaces a missing cell is
rejected even though the row count is right); every record agreeing with its plan cell
(configuration, size, replicate, seeds, budget, execution position, requested options); effective
options equal to what the released code runs; the current metric version; source hashes that are the
released ones or declared equivalent in `analysis/provenance-equivalence.json` (the move-budget
records were made before the generator's travel guard was added, and
`results/generator-identity.json` shows that both generator versions emit byte-identical
instances); spent budgets; and a feasibility flag consistent with the counters and filters. The
runner checks the retained witness with the full feasibility predicate (no hard violation **and**
no filter breach) before every run. `tests/safeguard-tests.mjs` feeds each of these failures to
the code and requires a rejection.

## Estimand

For an ablated configuration A and the complete solver B on replicate *i* (generator seed *i*,
solver seed 20 260 802 + *i*), with both runs feasible:
*d<sub>i</sub>* = *S<sub>i</sub>*(A) − *S<sub>i</sub>*(B) and, when *S<sub>i</sub>*(B) > 0,
*r<sub>i</sub>* = 100 *d<sub>i</sub>* / *S<sub>i</sub>*(B). A feasible pair with a zero baseline stays in
the absolute difference and is left out of the relative one only (counted as `excludedZeroBaseline`).
The reported effect is the mean of *r<sub>i</sub>* with an approximate two-sided 95 % Student-*t* interval
(four to ten pairs; treating the replicates as independent is a working assumption, since runs on one
host share its conditions). Positive means that removing the component makes the soft cost worse.
Feasibility is reported as counts. The interaction of two components is
*I<sub>i</sub>* = *S*<sub>11</sub> − *S*<sub>10</sub> − *S*<sub>01</sub> + *S*<sub>00</sub> over the four matched configurations,
and its relative form is the mean of 100 *I<sub>i</sub>* / *S*<sub>11,*i*</sub>.
